# Changelog

All notable changes to AutoRB will be documented in this file.

## [0.0075] - 2026-08-07
- **Album art is legible on every OS (root cause of the macOS 'scribbles' fixed).** The default "Chris Prime Custom" art hardcoded the Linux-only font path `/usr/share/fonts/truetype/dejavu/DejaVuSans-Bold.ttf`. On macOS that path doesn't exist, so `_font()` silently fell back to Pillow's built-in `load_default()` with **no size argument** → always the size-10 bitmap font: "CHRIS" rendered ~30×8px (~124 glyph px) instead of DejaVu's ~121×26px (~1858 glyph px), which is illegible when scaled up on the PS4 song list. The devcontainer always had DejaVu installed, so it looked fine — this was a latent mac-only portability bug, not a devcontainer regression (confirmed by a direct font-render test). DejaVu Sans Bold/Regular (permissively licensed, Bitstream Vera) are now **bundled** in the wheel (`autorb/export/data/fonts/`, shipped via `[tool.setuptools.package-data]`), and `_load_font()` prefers the bundled copy, then known OS paths (Homebrew/Library/macOS, `/usr/share/fonts/...`/Linux), and finally Pillow's scalable `load_default(size=)` (Pillow ≥ 10.1) — so the art renders identically everywhere, with no OS-font or Pillow-version dependence.
- **Circular "CP" monogram logo added to the bottom-right corner** of the default art (previously an unused corner): a thin orange ring containing a white "C" + "P" drawn as thick arcs/strokes, giving the generic cover a simple brand mark. The top-right "BOT" badge and center text are unchanged.
- **New regression tests:** `test_album_art_title_is_legible` asserts the title region has thousands of white glyph pixels on 256px art (fails if the render ever falls back to the tiny size-10 `load_default` font), and `test_album_art_has_cp_logo` asserts the bottom-right corner contains the orange ring + white glyphs. Full suite: **42 passed**.

## [0.0074] - 2026-08-07
- **MOGG build now fails fast with a clear message when ffmpeg lacks `libvorbis` (macOS fix).** Homebrew's standard `ffmpeg` formula dropped the `libvorbis` encoder in ffmpeg 8, so a fresh macOS user following the release notes hit `Unknown encoder 'libvorbis'` during `[5/5] Building assets...`. The multi-channel (10-ch) MOGG payload **requires** `libvorbis`: ffmpeg's built-in native `vorbis` encoder only supports 2 channels (and is experimental), so it cannot produce the 10-channel layout Rock Band requires. `mogg_builder.py` now probes `ffmpeg -encoders` up front (`_require_libvorbis()`, cached) and raises an actionable error pointing macOS users to install a libvorbis-capable build (`brew install ffmpeg-full`, which is keg-only so its `bin` must be put on PATH; or a [ffmpeg.org](https://ffmpeg.org/download.html) static build), plus the `ffmpeg -encoders 2>&1 | grep vorbis` verify command. README prerequisites and the CI release notes now document the macOS `ffmpeg-full` requirement instead of the plain `brew install ffmpeg` that no longer carries libvorbis.
- **Docs / roadmap:** README, CI release notes, and ROADMAP.md now call out the **vocal-phrase shortcoming** (phrase boundaries fall back to fixed 2-bar measure windows, making scoring feel wrong; each `.lrc` line timestamp marks the start of one vocal phrase and should be the source of truth, falling back to 2-bar only when the `.lrc` is missing/ambiguous) and the full roadmap: lyric/audio sync, one pitch per syllable, vocal pitch tracking (note moves with the voice), overdrive marking, and solo/Harmony 1/Harmony 2 detection + real instrument tracks.
- **Fix the wrong git clone URL in the `--build-pkg` error message** (was `chrispaiano/RockBandAutoSongLevelCreator`, "Repository not found"; corrected to `free5ty1e/RockBandAutoSongLevelCreator`) in `con_packer.py`, README, and the CI release body.
- **`tools/build_forgetool.sh` now fails fast with install instructions instead of `dotnet: command not found`.** It was hardcoding `/tmp/dotnet` on PATH (devcontainer-only) and never checking the toolchain; on a fresh git clone `dotnet` was missing and the build died cryptically. It now checks for both `dotnet` (.NET SDK 8) and `mono`, prints per-OS install commands (macOS: `brew install mono` + `brew install --cask dotnet-sdk@8`; Linux: `mono-devel` + the .NET 8 install script), and exits 1 with a pointer to re-run. README and CI release notes' `--build-pkg` prerequisites now list both .NET SDK 8 and Mono with concrete commands.
- **`tools/build_forgetool.sh` no longer hardcodes the Linux mono reference-assembly path.** It was passing `/p:FrameworkPathOverride=/usr/lib/mono/4.7.1-api`, which only exists on Linux; on macOS the build failed with `error CS0006: Metadata file '/usr/lib/mono/4.7.1-api/mscorlib.dll' could not be found`. The script now resolves the path via `find_framework_path()`: it builds a candidate list from `brew --prefix mono` (Homebrew, both Intel and Apple Silicon — e.g. `/opt/homebrew/Cellar/mono/6.14.1/lib/mono/4.7.1-api`), the Linux apt path `/usr/lib/mono/...`, and the old `/Library/Frameworks/Mono.framework/...` path, checks each for `mscorlib.dll`, and falls back to a `find` across the Homebrew Cellar and Framework roots if none of the fixed candidates exist. It prefers `4.7.1-api` first because `ForgeTool.csproj` targets `.NET Framework v4.7.1`. If nothing is found it prints actionable install guidance. **Prerequisites are now pinned to tested versions** so this can't silently break: `.NET SDK 8` (`dotnet-sdk@8` cask / `--channel 8.0`, already pinned) and **mono 6.x** (macOS Homebrew installs 6.14.1; Debian 12 / Ubuntu 22.04+ apt ships 6.8+/6.12+; mono must ship the `4.7.1-api` reference assemblies). Verified on the devcontainer (Linux resolves to `/usr/lib/mono/4.7.1-api`, clean from-scratch rebuild 0 errors) and by simulating the Apple-Silicon Homebrew layout (`brew --prefix mono` → `.../lib/mono/4.7.1-api`).
- **Bare-wheel installs no longer crash on `ModuleNotFoundError: No module named 'pkg_resources'`.** `resampy 0.4.2` imports `pkg_resources` at module load, and the wheel's own dependencies shipped no `setuptools`, so any run that reached `autorb.pitch.note_creation` (even `--skip-vocals`, which imports it at startup) failed on Python 3.12+ venvs where `pkg_resources` isn't bundled by default. The wheel now declares `setuptools>=68.0.0,<82.0.0` (setuptools **82 deletes** `pkg_resources`, so the upper bound is required; `requirements.txt` already had this pin). Verified: a clean `pip install` of the freshly built wheel into a new venv imports `resampy` + `pkg_resources` successfully, and the wheel's METADATA carries both `Requires-Dist: resampy<0.4.3,>=0.2.2` and `Requires-Dist: setuptools<82.0.0,>=68.0.0`.
- **`_find_forgetool()` no longer requires running from the repository root.** It previously checked only the CWD and its parent, so running the CLI from a parent of the clone (e.g. `temp/` with the clone at `temp/RockBandAutoSongLevelCreator/`) failed with "ForgeTool not found" even though the tool was built. It now searches (in order): the CWD and its immediate child dirs, every ancestor of the CWD up to the filesystem root, and `sys.prefix`/`sys.base_prefix` — returning the first `tools/forgetool` that exists. Covered by two new tests (`test_find_forgetool_child_and_ancestor`): running from the clone's parent (child search) and from a deep subdir inside the clone (ancestor walk).
- **ForgeTool CON→PKG no longer crashes on macOS with `DllNotFoundException: libgdiplus.dylib`.** ForgeTool reads the CON's album art (`_keep.png_xbox`) with `System.Drawing`, whose native backing is **libgdiplus**. Linux mono bundles it, but Homebrew's `mono` does **not**, so the first macOS `--build-pkg` run after the tool was found failed at `STFSPackage..ctor → Image.FromStream → GDIPlus`. Installing `brew install mono-libgdiplus` alone was insufficient: mono 6.x does not search Homebrew's lib dir (`/opt/homebrew/lib` on Apple Silicon) for native deps by default, so it still couldn't load the `.dylib` at runtime. The `tools/forgetool` wrapper now sets `DYLD_FALLBACK_LIBRARY_PATH` to `$(brew --prefix)/lib` on macOS (Harmless on Linux, where `DYLD_*` is ignored), so libgdiplus and its Homebrew deps (pango/cairo) resolve automatically. The wrapper's path resolution was also made portable (replaced GNU-only `readlink -f` with `cd ... && pwd -P`). `tools/build_forgetool.sh` additionally checks for `libgdiplus` and fails fast with `brew install mono-libgdiplus` (macOS) / `sudo apt install libgdiplus` (Linux). README and CI release notes list libgdiplus as a pinned prerequisite (macOS: `brew install mono-libgdiplus`; Linux: bundled with mono).
- **Tests:** full suite **40 passed** (39 prior + new `test_find_forgetool_child_and_ancestor`); devcontainer build process fully re-tested end-to-end (clean ForgeTool rebuild + CON→PKG conversion).

## [0.0073] - 2026-08-07
- **Vocal pitch accuracy overhaul (release-blocker: wrong note pitches / drifting vocal-fretboard scale on PS4).** The v0.0072 sync fix made the notes land on time, but the user still saw the vocal fretboard's *pitch* changing arbitrarily — many lyrics charted notes that don't match what the singer actually sang, so note-matching was impossible. Auditing the 284-word "Open Road Song" chart exposed why: pitches were taken straight from Basic-Pitch, whose Demucs-stem output is contaminated by harmonics, reverb, and guitar bleed (a `+0.1s` window extension routinely grabbed the *next* word's note — "as" charted the following word's 80), and the old pyin guard required `pyin_confidence >= 0.8`, so it **never fired (0/61 eligible words)**. The chart had 61/283 consecutive jumps ≥ 4 semitones (up to ±24) and a 33-semitone range.
- **`step4_sync.py` now picks each word's pitch from the most reliable source (validated on the real song):**
  1. **librosa pyin is primary.** For each word, pyin runs once over a window *clipped to the next word's charted start* (matching the charted note duration, so a word's window never leaks into a neighbour's). A reading is **trusted** only when ≥ 2 voiced, confident (`prob > 0.5`) frames exist AND the rounded mode is within 1 semitone of the median (`PYIN_MODE_AGREE_ST`). This keeps real vibrato/slides/sustained vowels while rejecting split readings caused by harmonics or bleed.
  2. **Basic-Pitch fallback, octave-snapped to the melodic contour.** Words without a trusted pyin reading fall back to a BP note, but the chosen note is snapped to the in-range octave copy nearest the **melodic contour** — a linear `interp1d` through the trusted words (constant extrapolation at the ends) — and accepted only if within 3 semitones (`CONTOUR_SNAP_ST`). This turns octave-flipped or contaminated BP notes into sane, in-key pitches.
  3. **Contour last.** If no BP candidate is close to the contour, the word follows the contour (clamped to the C3..C6 vocal range).
- **Removed the dead `_annotate_pyin_pitches` guard** from `vocals.py` (it cached per-word pyin over the *unrefined* WhisperX window, required conf ≥ 0.8, and was never invoked); step4 now computes pyin itself over the onset-snapped windows from the vocal stem.
- **Measured result on "Open Road Song":** consecutive jumps ≥ 4 st **61 → 28/283**, range **50..83 → 50..78**, max jump +24 → +14; **0/284 notes off the A-major scale**. Repeated phrases now sing the same notes (all "open"/"road" readings land near A3, the accented chorus "THIS is an open road" hits its real high G#4/F#5 climax), and pyin-confirmed melody is preserved (the low A2 on "As", the held F3 on "song", the F#5 "roaaaad").
- **New regression tests** (`tests/test_sync.py`): pyin trust (agreeing reading trusted, split reading rejected, window clipped to next word), melodic-contour interpolation + end extrapolation, octave-snap selection, pyin-over-BP precedence, contour fallback, vocal-range guarantee, and a full sine-wave-stem integration test proving pyin overrides a wrong-octave Basic-Pitch note. Old pyin-guard tests removed. Full suite: **39 passed**.
- **`--skip-mogg` no longer disables the count-in.** It previously forced `count_in_ticks/ms = (0, 0)`, so reusing an already-count-in'd cached MOGG produced a chart that was *not* shifted past the lead-in — the audio started ~4.5s late while lyrics/notes appeared immediately and the crowd booed (the exact bug it caused on PS4 during this cycle's rebuild). `--skip-mogg` now means *only* "skip MOGG encoding, reuse the cached `.mogg`" — the count-in is still derived from the cached beat grid (`count_in_params`, deterministic) and the chart is still shifted to match the reused MOGG's baked-in lead-in. Verified: rebuilt first vocal note tick 5884 (count-in 5760, 640-underflow check 5244), MOGG 202547ms = stems 198089 + 4458 count-in.
- NOTE: this changes vocal *pitch* only; the v0.0072 onset/time fixes are untouched, so the rebuilt chart's note timings are unchanged.

## [0.0072] - 2026-08-07
- **Vocal note overlap cascades (true root cause of the remaining in-game progressive drift found).** The v0.0071 sparse tempo map ruled out the tempo track — the rebuilt chart was verified self-consistent (grid ↔ tempo map ↔ ForgeTool `StartMillis` ↔ MOGG all agreed to <1ms) yet the user still heard every note after the first drift *progressively later*. Tracing the charted note ticks back through the tempo map exposed the real bug: `synced_track.json` word `end` times (which the sync step deliberately stretches across multi-syllable phrases) routinely extend **past the next word's start** — "Tonight" ends at 0.940s while "I" starts at 0.853s and "feel" at 0.975s. `generate_vocal_midi()` computed each note's duration from that end, set `last_tick = start + duration`, and emitted the next note at `max(target_start, last_tick)` — so every overlapping pair pushed every later note later, and the pushes **accumulated** across the whole song: index-aligned charted-vs-whisper drift grew 0 → +84 ticks → +11,143 ticks (0s → 5.2s → 8.4s) from first to last word. This exactly matches the PS4 symptom (first word right-on, then progressively late) and explains why the v0.0071 tempo-map change "didn't get any worse" — the drift was never in the tempo track. Fix: each note's duration is now **clipped to the next note's charted start** (a note whose end overlaps the following word ends at the next word's onset instead of pushing it), so every `note_on` lands exactly at its charted sung onset. Rebuilt charted-vs-whisper drift: med **+5.088s → 0.000s** (first/mid/last thirds all ≤ 68ms, onset-snap offsets only), and charted "open road song" words now land on the audio's real sung positions (48.1/50.8/80.0/85.6/91.3s) instead of 5-8s late.
- **New regression test** (`tests/test_vocal_midi.py::test_overlapping_word_ends_do_not_push_notes_late`): words whose `end` spans far past the next start must still have every `note_on` land exactly at `grid_to_tick(start)` and no note may overlap the next. Full suite: **33 passed**.

## [0.0071] - 2026-08-06
- **Sparse, measure-level tempo map (root cause of the remaining in-game progressive drift found).** The v0.0070 rebuild fixed the *offset* (first word of "Open Road Song" is now right-on on PS4), but the user still heard every subsequent note drift *progressively later*, the song-list preview stayed silent, and the Freestyle Vocals guide lines still never rendered. Binary comparison of our MIDI against two *working* references pinned the structural difference in the tempo track: stock **311 - Down** DLC carries **69** smooth `set_tempo` events (85.68-90.0 BPM) and the working custom **Smells Like Nirvana** carries **86** (118.64-126.32 BPM), spaced every 1-4 bars (1920-9600 ticks); our chart carried **391** events — one per beat (291 at 480-tick spacing) — whose values oscillate ~166.7/172.3 BPM every beat (plus a bogus 67 BPM beat at the count-in start and a 67-185 BPM overall range). The C3/RBN "Mix and MIDI Setup" guide confirms the requirement ("one tempo marker per measure"; an inaccurate map makes notes "feel far too late or early") — a dense, jittery, per-beat map is exactly the structure the game mishandles. `_build_tempo_grid()` now emits **one `set_tempo` event per measure** whose tempo is that bar's mean beat interval, skipping bars within ~0.5 BPM of the previous event (`TEMPO_MEASURE_TOL_US = 1000`). The rebuilt tempo track has **94 events** (spacing 1920/3840/5760/7680, matching the stock profile), a tight ~168-173 BPM body, and `grid_to_tick` is now the exact **inverse of the tempo-map integration** — chart and map are self-consistent by construction, so whatever tick a note is placed at, the game's tempo-map readback lands on the exact audio time charted (the raw beat grid's per-beat ±3 BPM alternation was beat-tracker noise, not musical tempo). First vocal note stays at tick 5884 (the user-confirmed-good word); only the tempo encoding changed.
- **Tests:** `test_dynamic_tempo_map_tracks_beat_grid` now asserts the map is *sparse* (fewer events than beats, all on 480-tick boundaries) and `test_dynamic_tempo_roundtrips_word_times` proves the chart/tempo-map round-trip is exact by construction. Full suite: 32 passed. Rebuilt `output/open_road_song.mid` (94 tempo events, 342 vocal notes, EVENTS/BEAT intact) and `output/pkg/UP8802-CUSA02084_00-0000000000000001.pkg` for PS4 retest.

## [0.0068] - 2026-08-06
- **Vocal onset snapping (fixes late words).** WhisperX word boundaries arrive systematically LATE (median ~80ms, tail up to ~400ms), so every word's start is now snapped to the nearest Basic-Pitch vocal-stem onset within a 0.45s-before/0.05s-after window — constrained to never snap more than 0.30s, and never back into the previous word's sung region (Basic-Pitch often merges a fast following word, e.g. "Tonight I", into one sustained note). Word ends extend across all notes that begin inside the word's own span so multi-syllable words keep their full sung window without stealing the next word's region. `synced_track.json` regenerated; the rebuilt chart's first vocal note (tick 6071 → 5.037s) lands within 7ms of the MOGG's first vocal energy peak (5.03s) and median stem-onset lag improved 60→55ms (p90 347→336ms).
- **Max-overlap vocal pitch selection.** `pitch_at` previously returned the weighted-median pitch, which let a spurious neighbour note sitting near the window centre drag the reading off the true sung note. It now picks the note with the largest overlap over the word's window — the sustained note wins over brief harmonics/echo bleed on Demucs stems. Pyin agreement improved 83% → 86% (125/149 → 139/160 words), octave-level errors (>4 st) down 15 → 11.
- **Pyin octave guard.** Words cached from a run that generated `vocals_cache.json` now carry per-word `pyin_pitch`/`pyin_confidence` (librosa pyin, C2..C6, voiced mask prob > 0.6), computed by the new `_annotate_pyin_pitches()` in `vocals.py`. When pyin is genuinely confident (≥ 0.8) and disagrees with Basic-Pitch by more than 4 semitones, the pyin reading overrides — fixing the octave-flipped words while leaving ambiguous stem artifacts (where both estimators themselves flip) untouched. All pitches stay clamped to the C2..C6 vocal range.
- **Feature Support Matrix in README.** Documents exactly where ForgeTool-gated features work: CON generation/stems/tempo/vocals/difficulty/count-in/MOGG/songs.dta everywhere; `--build-pkg` and the PS4 freestyle-vocals guide lines only on a git checkout or devcontainer (ForgeTool is vendored source-only, rebuilt by `tools/build_forgetool.sh`; the wheel ships no ForgeTool and `--generate-freestyle-vocals` is a no-op for PS4 on a bare wheel).
- **Tests:** new `tests/test_sync.py` (9 tests) covers onset snapping (nearest-onset, prev-word rejection, max-shift cap, end extension), max-overlap pitch selection, the pyin guard's confidence and disagreement thresholds, the octave correction, and vocal-range clamping. Full suite: 26 passed. CON `stfs_validator.py` VALID; rebuilt PKG's `songdta_ps4` still reports `HasFreestyleVocals=1`.

## [0.0067] - 2026-08-05
- **`--generate-freestyle-vocals`: RB4 freestyle guide lines, root cause found.** The PS4 test showed the "diatonic guide lines" (Hard/Expert vocals) never rendered. Research disproved the old theory that `(vocal_tonic_note N)` + `(song_tonality 0|1)` in `songs.dta` enable them: the PS4 `songdta_ps4` binary format has **no slot** for those fields, and `SongDataConverter.ToSongData` silently drops them (they're RB3-only metadata). The RB4 manual confirms the guide lines are the **Freestyle Vocals** feature, gated **per-song** ("available for songs that support it, as indicated in the Music Library"), and the `songdta_ps4` binary carries the `HasFreestyleVocals` bool for exactly that. Upstream ForgeTool hardcoded it to `false`, so no ForgeTool-converted custom ever advertised freestyle support.
- **Patched the vendored ForgeTool** (`tools/libforge/.../SongDataConverter.cs`): `HasFreestyleVocals = songDta.Array("freestyle_vocals")?.Int(1) == 1`. The new `--generate-freestyle-vocals` CLI flag makes `generate_songs_dta()` write `(freestyle_vocals 1)` into `songs.dta`; without it the field is omitted and the flag stays `false`. Once enabled, the game itself computes the guide scale from the charted vocal notes (root/3rd/5th interval shading per Harmonix patent US 2010/0304810).
- **Patched ForgeTool propagates automatically.** ForgeTool is vendored as **source** and rebuilt on every fresh devcontainer (`.devcontainer/post-install.sh` → `tools/build_forgetool.sh`); the wheel never ships ForgeTool binaries (`--build-pkg` requires a git clone), so any fresh clone of the tag gets the patched source too. No binary distribution needed.
- **Verified end-to-end:** regenerated the CON/PKG with the flag and parsed the built `songdta_ps4` — `HasFreestyleVocals=1` with the flag (was `0` on the pre-patch artifact), `0` when the flag is omitted; CON `stfs_validator.py` VALID; new `tests/test_dta_writer.py` covers flag written/omitted. Full suite: 17 passed.
- **Wiki correction:** `rock_band_customs_domain.md`, `architecture.md`, `vocal_alignment.md`, and `forgetool_compat.md` now document the real mechanism and mark the `vocal_tonic_note`/`song_tonality` guide-line theory as disproven for PS4.
