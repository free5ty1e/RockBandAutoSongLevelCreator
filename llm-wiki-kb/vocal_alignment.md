# Vocal Alignment & LRC Processing

## Standard vs. Enhanced LRC
- **Standard LRC:** Provides line-level timestamps. Example: `[00:12.00] This is an open road song`
- **Enhanced LRC:** Provides word/syllable-level timestamps. Example: `[00:12.00] <00:12.00> This <00:12.20> is <00:12.40> an <00:12.60> o<00:12.70>pen <00:13.00> road <00:13.50> song`

## AutoRB's AI Alignment Strategy
Rock Band requires MIDI events for every spoken syllable so the in-game lyric tubes scroll correctly. Standard LRCs are insufficient. 

To solve this:
1. AutoRB ingests the user's Standard LRC (which provides the 100% accurate lyrics, avoiding AI hallucination on the text itself).
2. The pipeline extracts the `vocals.wav` stem.
3. A forced-alignment model (like WhisperX) listens to the vocal stem and maps precise start/end timings to the words provided in the Standard LRC.
4. This data is mapped to MIDI pitch notes on the `PART VOCALS` track. Each `synced_lyrics` entry now carries real `start`/`end` (from the word segments) and `pitch` (from the Basic-Pitch `note_events` in `vocals_cache.json`, **max-overlap** note lookup, v0.0068) — `step4_sync.py` emits these fields explicitly (v0.0061). Before that fix the entries only had `time`/`beat_time`, so `generate_vocal_midi()` fell back to `start=0.0`, `pitch=60` for every word and the entire 284-note chart was a blob at tick 0 (the "fretboard flashes then instant 0%" symptom).

## Onset-Snapped Timing & Pyin Guard (v0.0068 → v0.0070)
WhisperX word boundaries are systematically LATE relative to the true sung onset (median ~80ms, tail up to ~400ms), which reads as lyrics/notes drifting behind the audio in-game. `step4_sync.py` snaps each word's start to a real vocal onset within a 0.45s-before / 0.05s-after window (`_refine_word_timing`), with two hard constraints:
- **Never back into the previous word's sung region** (`prev_sung_end - MIN_WORD_GAP`) — Basic-Pitch often merges a fast following word (e.g. "Tonight I") into a single sustained note, and snapping into that note would steal the neighbour's sung window.
- **Only when WhisperX is measurably late** (`ONSET_SNAP_EARLY_MIN` = 0.03s) — an on-time alignment is left alone.

**v0.0070 root cause: Basic-Pitch onsets are themselves late.** The v0.0068 snap chose the *nearest* Basic-Pitch note onset, but Basic-Pitch misses the earliest part of the sung attack (consonant + first energy). On Eve 6 "Open Road Song" the singer attacks "Tonight" at **0.23s** (librosa onset on the vocal stem; confirmed by RMS ramp), WhisperX aligned the word at **0.61s**, and Basic-Pitch's first onset was **0.58s** — so the nearest-onset snap moved the note only 30ms, leaving it **~350ms late** (charted 5.037s vs real sung onset ≈ 4.68s) on top of the ~80ms median lag across all 284 words. The v0.0069 "file is internally consistent" conclusion was right but incomplete: word↔note↔MOGG agree *because all three share the late sources*. The ground truth is the stem's attack.

**Fix:** `step4_sync.py` now runs librosa onset detection on the vocal stem (`_detect_vocal_onsets`, sr=22050, `onset_strength` + `onset_detect(backtrack=True, delta=0.05)`) and snaps each word's start to the **earliest** onset in the search window (the true attack), still bounded by the previous word's sung end. The nearest-Basic-Pitch snap is retained only as a fallback when no stem is available. `cli.py` passes `stems["vocals"]` into `run_step_4(...)` so the snap always uses the real stem (works with `--skip-vocals` cached runs). Result: first word charts at 0.232s; median word-vs-onset lag dropped **80 → 20ms**; charted first note now lands ≈ the actual sung onset.

Word ends extend across all notes that *begin inside* the word's own span, so multi-syllable words keep their full pitch window without widening into the next word. Words are processed in chronological order and `prev_sung_end` tracks the charted end so the constraint is strict.

**Pitch = max-overlap note.** Demucs vocal stems carry reverb/bleed, so Basic-Pitch emits several simultaneous notes (one true vocal, the rest harmonics/echo). The v0.0061 weighted-median lookup let a spurious neighbour near the window *centre* drag the reading off; the v0.0068 `pitch_at` picks the note with the largest overlap over the word window — the sustained sung note wins.

**v0.0073 root cause: Basic-Pitch (via `pitch_at`) is a poor *primary* pitch source.** After the v0.0072 sync fix landed, the PS4 user still saw the vocal fretboard *pitch* changing arbitrarily — many lyrics charted notes that don't match what the singer actually sang. Auditing the 284-word "Open Road Song" chart showed pitches were taken straight from Basic-Pitch, whose stem output is contaminated by harmonics, reverb, and guitar bleed; a `+0.1s` window extension routinely grabbed the *next* word's note ("as" charted the following word's 80). The chart had 61/283 consecutive jumps ≥ 4 st (up to ±24) and a 33-st range. The old pyin guard (below) required `pyin_confidence >= 0.8` and so **never fired (0/61 eligible words)**.

**v0.0073 fix: per-word pyin is primary, BP is an octave-snapped fallback, contour is last.** `step4_sync.py` now computes the full pitch in `_resolve_pitches` over each word:
1. **librosa pyin is primary** — runs once per word over a window *clipped to the next word's charted start* (mirroring the charted note duration, so a word's window never leaks into a neighbour's). A reading is **trusted** only when ≥ 2 voiced, confident (`prob > 0.5`) frames exist AND the rounded mode is within 1 semitone of the median (`PYIN_MODE_AGREE_ST`). This keeps real vibrato/slides/sustained vowels while rejecting split readings (fundamental + strong harmonic).
2. **Basic-Pitch fallback, octave-snapped to the melodic contour** — for words without a trusted reading, the max-overlap BP note (full `[start,end]` span, as in the validated prototype) is snapped to the in-range octave copy nearest the **melodic contour** (a linear `interp1d` through trusted words, constant extrapolation at the ends) and accepted only within `CONTOUR_SNAP_ST` (3 st). This turns octave-flipped/contaminated BP notes into sane, in-key pitches.
3. **Contour last** — if no BP candidate is near the contour, the word follows the contour, clamped to C3..C6 (`VOCAL_MIDI_MIN/MAX` = 48/84).

Measured on "Open Road Song": consecutive jumps ≥ 4 st **61 → 28/283**, range **50..83 → 50..78**, max jump +24 → +14, **0/284 off the A-major scale**, and repeated phrases now sing the same notes while pyin-confirmed melody is preserved (low A2 on "As", held F3 on "song", F#5 "roaaaad"). The old `_annotate_pyin_pitches` guard in `vocals.py` was removed (step4 computes pyin itself over the onset-snapped windows); the "This [67.5] / is [56.2]" example below is a *genuine* melodic accent, not an artifact to suppress.

Measured on Eve 6 "Open Road Song" (v0.0070): first word "Tonight" charts at 0.232s ≈ the true 0.23s sung attack (was 0.58s pre-v0.0070); median word-vs-onset lag 20ms (was 80ms). Remaining PS4-side symptoms (song-list preview silence, freestyle guide lines not rendering) are tracked separately in `rock_band_customs_domain.md` and `ps4-environment.md`.

## Overlap-Free Note Ends (v0.0072 root cause of the remaining in-game drift)
The onset snap (v0.0070) and the sparse tempo map (v0.0071) shipped, but the PS4 symptom stayed: first word right-on, every subsequent word *progressively later*. The tempo track was exonerated (the rebuilt chart round-tripped grid↔tempo-map↔ForgeTool `StartMillis`↔MOGG to <1ms), so the drift had to be in the note *positions* themselves. Tracing the charted note ticks back through the tempo map exposed it: `step4_sync.py` deliberately stretches word `end` times across the word's whole phrase (line 25 above), so a word's end routinely runs **past the next word's start** — "Tonight" ends at 0.940s while "I" starts at 0.853s and "feel" at 0.975s. `generate_vocal_midi()` computed each note's duration from that end, kept a running `last_tick = start + duration`, and emitted each note at `max(target_start, last_tick)`. Every overlapping pair therefore pushed the following note later, and the pushes **accumulated** across the whole song: index-aligned charted-vs-whisper error grew 0 → +84 → +11,143 ticks (0s → 5.2s → 8.4s) from first word to last — exactly the PS4 rate problem, and why the v0.0071 tempo change "didn't get any worse" (the drift was never in the tempo track).

**Fix:** `generate_vocal_midi()` precomputes every word's charted start/end ticks, then **clips each note's end to the next note's charted start** before emitting, so a note whose end overlaps the following word simply ends at the next word's onset instead of pushing it. Every `note_on` now lands exactly at `shifted_time_to_tick(start)` — its true sung onset. Rebuilt charted-vs-whisper error: med **+5.088s → 0.000s** (first/mid/last thirds all ≤ 68ms, onset-snap offsets only), and the charted "open road song" words land on the audio's real sung positions (48.1/50.8/80.0/85.6/91.3s) instead of 5-8s late. Regression test: `tests/test_vocal_midi.py::test_overlapping_word_ends_do_not_push_notes_late`.

## Placeholder Instrument Tracks (required for RB4)
The `.mid` chart emitted by `generate_vocal_midi()` also includes placeholder `PART DRUMS`, `PART GUITAR`, and `PART BASS` tracks even though the vocals pipeline does not chart real instruments. Rationale: `songs.dta` advertises drums/guitar/bass at rank 150, and RB4 (via ForgeTool PKG conversion) crashed when the vocal fretboard loaded if an advertised part had no corresponding MIDI track. Every instrument advertised in `songs.dta` must have a loadable chart track, even if it is just a placeholder. The MIDI header track count is now 7 (v0.0061), mirroring "311 - Down": track 0 = tempo map (named `song_id`, 4/4 + 120 BPM), then `PART DRUMS`, `PART GUITAR`, `PART BASS`, `PART VOCALS`, `EVENTS`, `BEAT`. The `EVENTS` track carries the mandatory text markers `[prc_intro]`, `[music_start]`, `[prc_verse_1]`, `[preview]`, `[prc_chorus_1]`, `[prc_outro]`, `[music_end]`, `[end]` and the `BEAT` track carries one quarter-note marker per beat (pitch 12 downbeat vel 101, pitch 13 vel 100, 480-tick spacing).

Each placeholder track (`build_placeholder_track()` in `midi_generator.py`) emits one note per difficulty using `PLACEHOLDER_DIFFICULTY_PITCHES = (60, 72, 84, 96)` — EasyStart=60, MediumStart=72, HardStart=84, ExpertStart=96, matching the difficulty start keys in LibForge's `RBMidConverter.cs`. This is mandatory: `RBMidConverter` (`HandleDrumTrk` / `HandleGuitarBass`) stores `gem_tracks` as a 4-element difficulty array (Easy/Medium/Hard/Expert) that is filled lazily only when a note for that difficulty is seen, then runs `gem_tracks.Select(g => g.ToArray()).ToArray()` (RBMidConverter.cs:606 and :975). A single note at pitch 60 filled only the Easy slot, leaving Medium/Hard/Expert null and throwing `System.NullReferenceException` during ForgeTool "CON to PKG Conversion" (fixed in v0.0057).

## LRC Lines as the Phrase Source of Truth (highest-priority roadmap item)
Rock Band phrases are 2-bar (or 4-bar) windows on the beat grid, but the *natural* phrase boundaries come from the song's lyric lines. Design decision: each line of the user's `.lrc` file should define one vocal phrase (open the phrase at the first word of the line, close at the last word's end), with measure-based windows as the fallback only when the `.lrc` is missing or doesn't make phrasing obvious. This keeps phrasing musical (verse lines, chorus lines) instead of rigid fixed windows. **Current limitation:** phrase boundaries fall back to fixed 2-bar measure windows, so in-game phrase regions and vocal scoring feel wrong — each `.lrc` line timestamp marks the start of one vocal phrase and should be the source of truth.

## WhisperX Small-Word Misplacement (known weakness)
WhisperX forced alignment occasionally lands a short word (e.g. "I", "a", "the") at the end of the *previous* phrase instead of the start of the *next* one, because its alignment cost favors the nearer vowel. When LRC lines drive phrasing, words need **re-anchoring to their LRC line**: if a word's aligned position falls outside its LRC line's time span, snap it to the line boundary (start of its own line, or end of the previous line) rather than trusting the raw alignment.

## Vocal Key Detection (v0.0063) & Freestyle Gating (v0.0067)
`autorb/export/key_detect.py` runs Krumhansl-Schmuckler key-finding on the Basic-Pitch `note_events` (pitch classes weighted by note duration, rotated key profiles compared by cosine similarity) and returns `(tonic_pitch_class, tonality)` — 0-11 chromatic (0=C) and 0=major/1=minor. These feed `(vocal_tonic_note N)` and `(song_tonality 0|1)` in `songs.dta`. Eve 6's "Open Road Song" detects as A major (tonic 9, tonality 0). **Correction (v0.0067):** these dta fields are *not* what enables RB4's "Acceptable Pitch" guide lanes — they have no slot in the PS4 `songdta_ps4` binary and are dropped by `SongDataConverter`. On PS4 the guide lanes are gated by `HasFreestyleVocals` in `songdta_ps4` (written by `SongDataWriter.cs:42`); the game computes the guide scale from charted vocal notes per Harmonix patent US 2010/0304810 once the feature is enabled. AutoRB's `--generate-freestyle-vocals` flag writes `(freestyle_vocals 1)` into `songs.dta`, which the patched vendored ForgeTool reads into `HasFreestyleVocals`. See `rock_band_customs_domain.md`.

## Mandatory Count-In (v0.0064)
Rock Band charts are not allowed to start musical content at tick 0. Stock RB3 DLC bakes a silent lead-in into the MOGG audio (311 - Down has ~5s of silence before its first note, with `[music_start]` at tick 5280), and the game/gamertag/lyrics all assume that pre-roll exists. AutoRB now reproduces it:
- `mogg_builder.build_mogg_from_stems(..., count_in_ms)` prepends silence to all 10 channels via ffmpeg `adelay={count_in_ms}:all=1`.
- `midi_generator.count_in_params(beat_times)` sizes it from the song's opening beat-grid tempo: **3 measures (12 beats)** per the C3 authoring guide's >=160 BPM rule. Eve 6's "Open Road Song" (161.5 BPM opening) → 4458 ms / 5760 ticks.
- `generate_vocal_midi(..., count_in_ticks)` shifts every chart event (vocal notes, phrase markers, `EVENTS`, `BEAT`, tempo map) past the count-in. `[prc_intro]`/`[music_start]` land at `count_in_ticks` instead of tick 0.
- `--skip-mogg` reuses an existing `.mogg` (which was already built WITH this count-in lead-in baked in), so the count-in is still computed from the cached beat grid and the chart is still shifted past it — keeping the rebuilt chart and reused audio in sync. `count_in == 0` only when there is no usable beat grid (v0.0073: it is no longer forced to 0 under `--skip-mogg`).

### Why the first phrase underflow broke the vocal guide
ForgeTool's `RBMidConverter.cs:1286` computes phrase start times as `e.StartTicks - 640` on a `uint`. When a chart's first phrase marker sat at tick 311 (our pre-0.0064 charts started content at tick 0), `311 - 640` wrapped to `4294966967`; `GetMillis` then returned end-of-song (~198s), so the first phrase's StartMillis landed at the end with a negative length (`RBMidWriter.cs:197` writes StartMillis/LengthMillis verbatim). The fix is structural, not a constant `+640` shift (which is impossible anyway: `MidiHelper.cs:23-31` does `idx--` on the tempo map and crashes with index -1 if tick 0 has no tempo entry). Moving the first phrase to tick 6071 makes `6071 - 640 = 5431` safe.
