# Resolving ForgeTool GUI CON Parsing Errors

## Background and Root Cause Analysis
I have performed a deep binary analysis comparing the `open_road_song.con` generated by `con_packer.py` against the known-good `SmellsLikeNirvana_rb3con` and `311 - Down` packages.

The errors you've been seeing in ForgeTool GUI (`Element at index 0 is not an Array. It is DataSymbol`, `Object reference not set to an instance of an object`, etc.) are **not** caused by text formatting issues within `songs.dta`. Instead, they are caused by **fundamental STFS container corruption**.

Currently, `con_packer.py` takes a template CON file and linearly overwrites the file payloads starting at offset `0xD000`:
```python
        payload_offset = 0xD000 + start_block * BLOCK_SIZE
        padding_space = block_count * BLOCK_SIZE
        con_data[payload_offset : payload_offset + padding_space] = b'\x00' * padding_space
        con_data[payload_offset : payload_offset + size] = new_content
```

### Why this breaks:
1. **Hash Table Overwriting:** The Xbox 360 STFS format is not a contiguous file system. It intersperses 4KB "Hash Table" blocks every 170 data blocks to ensure integrity. Your `.mogg` file is 3,547 blocks long, which means `con_packer.py` blindly writes the audio data straight through ~20 hash tables, corrupting both the STFS structure and the audio file itself (as extractors will skip the hash blocks, dropping 4KB of audio at a time).
2. **Invalid SHA-1 Hashes:** STFS relies on a Merkle tree of SHA-1 hashes (Top Hash -> L1 Hashes -> L0 Hashes -> Data Blocks). Because `con_packer.py` does not compute or update these hashes, ForgeTool validates the hashes upon extraction, fails, and returns corrupted/zeroed buffers. When ForgeTool's DTA parser attempts to read this corrupted binary garbage, it throws parsing exceptions like `Element at index 0 is not an Array`.

> [!WARNING]
> While you attempted to preserve the RSA signature by cloning the template, an STFS container with valid RSA signatures but corrupted internal data blocks and hashes is completely invalid. PC tools like ForgeTool only care about the internal SHA-1 hash integrity for extraction, not the cryptographic RSA signature.

## Proposed Implementation Plan

I will completely rewrite `con_packer.py` to properly build an STFS container from scratch in Python. The new packager will:
1. **Allocate blocks correctly:** It will track block indices and automatically skip and reserve blocks for Level 0 and Level 1 hash tables (every 170 and 28,900 blocks respectively).
2. **Compute SHA-1 Hashes:** As data is written, it will compute the SHA-1 hash of each 4KB data block, populate the Level 0 Hash Tables, hash those to populate the Level 1 Hash Tables, and finally compute the **Top Hash**.
3. **Update the Volume Descriptor:** It will correctly populate the Volume Descriptor at offset `0x379` with the newly computed Top Hash, Total Allocated Block Count, and File Table Start Block.
4. **Maintain Compatibility:** It will preserve the base metadata header of `SmellsLikeNirvana_rb3con` (to satisfy ForgeTool's basic header checks) but inject a fully valid, dynamically generated STFS block stream.
